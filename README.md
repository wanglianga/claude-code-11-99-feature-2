# 夜间寝具柜台

供**仓管员、柜台职员、稽核员**共同操作的寝具发放工作台：家庭按实际住宿人员领到**一垫一毯**，并办理退回、拆包与补领。**提前封家庭包**与**居民到柜后现场拣配**两种工作方式都可操作。

纯浏览器前端：React + TypeScript + IndexedDB + WebWorker，计算与持久化全部在本地完成，不依赖后端，不使用真实居民资料（内置虚构物资编号与虚构家庭）。

## 领域规则实现要点

- **内部模型（已选定一套）：有根包含树**。每件垫子/毯子（叶件）与每个包都是树节点；只有根节点持有位置（库房 / 领取柜 / 已交付 / 待清洁 / 报损），包内物资位置随根继承——**整包搬运只改一个根**（四人包到柜 = 更新 1 个根位置，8 件物资位置随根继承）；**核查单件沿父链解析祖先**（逐件追踪页展示完整包含链）。仓管不面对第二套模型。
- **目录与成套约束**：单件、一人套包（恰 1 垫 1 毯）、四人包（恰 4 个一人套）；重封包用于开封后重新封装。成套只覆盖其内部物资，一人套不能再额外增加一垫一毯（引擎按组成核验拒绝）。**包壳本身不计寝具**：所有物资计数只按叶件（垫/毯）。
- **包含树不变量**：包含关系不成环、一件不能有两个当前父包（装入即改挂）；封签完好 ⇒ 子树未动（跨层拆包须自外而内；退回取件时祖先封签自动失效并留痕）；不会出现“包已交付而子件仍可用”（已交付包不能开封/取件/移动，子件随交付锁定）。
- **需求与领取权**：每人每住宿批次一垫一毯；需求与人绑定、**与家庭归属分开**——拆成两户只改归属，需求单号不变、凭证份数合计不变，**不重新生成领取权**。
- **交付原子核销**：交付在同一事务内完成「实际物资 ↔ 领取凭证 ↔ 需求覆盖」核销。整包交付超出凭证人份的物资**先记待返还**，**清点实收且确认为未用**才回库可重发；已用入待清洁、报损入报损。对照路径：现场按人拣配则不多发，余量可直接给后来的家庭。
- **补领**：须填原因；换发新件不新增凭证核销（响应丢失查原交付、不再领一次）；**旧物实际退回后才能进入清洁或报损**——申请提交时旧件仅标记「待退回」，不离开已交付态；同一需求同一品类的**重复补领**会被核对拒绝。
- **两个计数可核对**：需求覆盖按人算、物资数量按叶件算；每个计数都可追到实物（物资编号）与操作者（回执含角色与时间）。右侧「全柜核对」面板实时校验六类不变量。
- **多标签并发**：同一站点多标签共享 IndexedDB；所有写命令在单个 readwrite 事务内「读取→校验→写回」，跨标签天然串行——一个标签整包交付某四人包后，另一标签对同包的开封/取件在事务重核中得到明确冲突结果（反之亦然）。
- **幂等**：每条命令携带 commandId，重复提交只生效一次并开具「重复回执」。

## 本地启动

要求 Node 18+（推荐 22）。

```bash
npm install        # 安装依赖
npm run dev        # 开发模式：http://localhost:5173
```

其他命令：

```bash
npm run test       # 运行领域引擎单元测试（vitest，19 个用例）
npm run build      # TypeScript 检查 + 生产构建到 dist/
npm run preview    # 预览生产构建：http://localhost:4173
```

## Docker 一键启动

```bash
docker compose up --build
# 打开 http://localhost:8080
```

（等价地：`docker build -t bedding-counter . && docker run -p 8080:80 bedding-counter`。镜像为多阶段构建：Node 构建静态产物，Nginx 托管，无需任何后端服务。）

## 演示账号（角色）

无需账号密码。页面右上角下拉即可切换三个演示角色，权限由引擎在事务内再次校验：

| 角色 | 权限 |
| --- | --- |
| 仓管员 | 封包 / 开封 / 包内取件 / 库房↔领取柜移动 / 完成清洁 |
| 柜台职员 | 登记家庭、拆分家庭、交付核销、退回接收、补领换发 |
| 稽核员 | 只读（查看全部页面、核对面板与回执流） |

任何角色都可推进演示时间、重置演示数据。

## 演示脚本（对应题目要求的验证场景）

初始场景（演示时间 21:00，夜间开柜）：库房有四人包 PK4-01、PK4-02（各含 4 个一人套共 8 件）、散件一人套 SET-11/12、散垫 6 件、散毯 6 件；家庭：周明一家 3 人、吴刚一家 3 人、郑钱家 2 人、陈军一家 4 人、林浩家 2 人（各持同人数领取凭证）。

1. **整包到柜与开封重封**（仓管员 · 封拆包装页）：PK4-01「送到领取柜」——回执注明“整包移动：仅更新 1 个根节点位置，8 件物资位置随根继承”。对 PK4-01「开封」→「取出」SET-01 → 勾选 SET-02/03/04 选「重封包」封装 → RPK-01（6 件在包内）＋ SET-01（2 件在现场），PK4-01 成为空包壳（不计寝具）。
2. **整包交付超发 → 待返还 → 清点重发**（对照路径 A）：重置后把 PK4-01、PK4-02 送到领取柜；柜台职员在「领取交付」页给周明一家交付 PK4-01、给吴刚一家交付 PK4-02——各核销 3 人份，共多出 2 人份记「待返还」。在「退回与补领」页对两家各退回 1 垫 1 毯并验收「未使用」→ 待返还清讫、物资回库可重发（可再交付给郑钱家）。
3. **现场拣配对照**（对照路径 B）：重置后两包到柜并开封、取出全部 8 个一人套；周明一家拣 3 套、吴刚一家拣 3 套（恰好核销，**无待返还**），余 2 套直接交付给后来的郑钱家（2 人）。
4. **套散混用**：SET-11 ＋ 散垫 MAT-101 ＋ 散毯 BLK-101 到柜后一起交付给林浩家（2 人全覆盖）。
5. **缺垫多毯**：给郑钱家交付 MAT-101＋BLK-101＋BLK-102——孙丽有毯无垫记为未覆盖（多毯不抵垫、也不算超发）；再补发 MAT-102 后全覆盖。
6. **跨层拆包**：四人包未开封时直接拆一人套被拒（须自外而内）；开封四人包 → 取出一人套 → 再开封一人套 → 取出垫子。
7. **整包交付与取单件并发**：开两个浏览器标签（同一地址），都把 PK4-01 送到领取柜；标签 A 交付 PK4-01，标签 B 同时对 PK4-01 开封——后到者在事务重核中被拒（“包已交付，不能开封”）；重置后反过来操作（先开封），则整包交付被拒（“包已开封，包壳不能整包交付”）。
8. **家庭拆分**：陈军一家先领 2 人份，再在「人员需求」页把陈大、陈二拆出为新户——凭证 4 份 → 2＋2（合计不变），已核销随覆盖转移，需求单号不变。
9. **补领与重复核对**：林浩家领取后，在「退回与补领」页为赵敏的毯子提交补领（原因必填，如“被水浸湿”）→ 新毯立即换发、旧毯标记「待退回」且仍在已交付态（申请≠已回）；再次对同一人同一品类补领被拒（重复补领核对）。旧毯实际退回（验收已使用）后才进入待清洁，补领闭环；仓管员「完成清洁」后回库。
10. **幂等**：交付成功后点「模拟重复提交上次交付」（相同 commandId 重发）→ 只产生“重复提交已幂等忽略”回执，交付单与核销不变。
11. **逐件追踪**：在「逐件追踪」页搜索任意物资编号（如 MAT-001），查看其状态、位置（解析祖先）、包含链、原交付单、补领记录与相关回执；包与包壳单列（不计寝具）。右侧「全柜核对」全程实时校验。

## 架构与目录

```
src/
  engine/           # 纯函数领域引擎（UI 与 Worker 共用同一口径）
    types.ts        # 领域模型与命令定义（包含树节点、需求、凭证、交付、待返还、补领）
    seed.ts         # 虚构演示数据（两个四人包 + 散件 + 五个家庭）
    engine.ts       # 派生计算（祖先解析/叶件统计/交付预演）、命令处理、全柜核对
    format.ts       # 时间格式化
  worker/           # WebWorker：所有写操作在此串行落库
    store.ts        # IndexedDB 单记录事务（读取→校验→写回）
    worker.ts       # 命令分发 + 多标签失效广播
  ui/               # React 工作台
    client.ts       # Worker 客户端 + BroadcastChannel 多标签同步
    App.tsx         # 主界面（角色、时钟、页签、右侧核对与回执栏）
    components.tsx  # 统计条 / 回执流 / 全柜核对等通用件
    pages.tsx       # 五个页面：封拆包装 / 人员需求 / 领取交付 / 退回与补领 / 逐件追踪
  test/
    engine.test.ts  # 19 个领域引擎测试
```

关键设计：

- **单记录事务状态**：整份状态存于 IndexedDB 单条记录，命令在事务内完成「读→引擎校验→写回」，多标签并发由 IndexedDB 序列化，杜绝脏写。
- **交付预演共用**：UI 的交付预览与引擎的交付处理调用同一个 `planDelivery`，页面看到的“将覆盖 N 人 / 超出 M 件记待返还”与事务内实际核销完全一致。
- **虚拟时钟**：回执与业务时间使用可推进的演示时钟，便于演示夜间开柜流程。
- **数据安全**：全部数据仅存于本浏览器 IndexedDB，清除站点数据即可彻底删除；无任何网络请求与后端依赖。
